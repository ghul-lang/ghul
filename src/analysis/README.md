# Analysis mode and language service

The code in this folder lets the compiler act as a lightweight language service. When the driver starts with `--analyse`, `Analysis.ANALYSER` reads commands from standard input and responds over standard output. These commands mirror typical language server requests (hover, definition lookups, completions and so on) and ride a **newline-delimited JSON protocol**: one JSON object per line, `\n`-terminated. Requests and responses are both discriminated by a `kind` field naming the variant in lower case.

The main components are:

- `analyser.ghul` – entry point that drives a `COMMAND_DESPATCHER` loop.
- `request_reader.ghul` – lifts request frames off standard input on a thread of its own and queues them, so the despatcher can see what is waiting rather than only what it has already asked for. Deserialization happens there too, so a malformed line arrives as a queued `PARSE_ERROR` rather than as an exception at whatever point the despatcher read. Nothing else about the analyser is concurrent: every request is still handled on the main thread, one at a time.
- `command_despatcher.ghul` – takes the next queued frame and dispatches it to the matching handler. Also serves the queries that arrive mid-compile — see below.
- `command_handlers.ghul` – implements individual requests such as `hover`, `definition` and `edit`. Each handler builds a typed response DTO and emits it via `JSON_PROTOCOL` as a single line.
- `protocol/` – the small `JSON_PROTOCOL` helper with the deserialize-request / write-one-line primitives, which read and write the protocol types through the runtime's reflective `Json` serializer, matching the JSON the client's `JSON_OPTIONS` reads and writes. The request and response DTOs themselves live in `analysis-protocol/` at the repo root, shared with the analysis-tests client via a project reference. The `diagnostics_collector.ghul` neighbour renders the diagnostics store into the typed `DIAGNOSTIC[]` carried by the `diagnostics` response.
- `quick_fix_synthesizer.ghul` – builds ready-to-apply quick fixes for coded diagnostics: a preferred removal edit for the redundant-operator warnings, and a `@suppress("<code>")` insertion per enclosing scope for every coded diagnostic. The compiler is the sole author of fixes; IDE clients apply what arrives without per-code knowledge, so new fixes need no client change. Driven by the `code_actions` request rather than by the diagnostics path: synthesis sweeps the whole AST of every file holding a coded diagnostic, so attaching fixes to reported diagnostics cost the whole project on every keystroke and threw nearly all of it away. Clients gate the request on the `code-actions` capability in the `listen` frame.
- `watchdog.ghul` – decides when the analyser should recycle: on a sustained burst of handler exceptions, or on managed-heap growth past a threshold. The heap is sampled on an explicit `heap_check` request (the IDE sends one during a lull in editing) and, as a fallback, periodically after compiles.
- `memory_usage` answers the bytes the process occupies (resident or working set, not the managed heap) without collecting. Clients gate the request on the `memory-usage` capability in the `listen` frame; a figure of 0 means the host cannot say.
- `report_progress` turns on two frames that answer no request: `rebuilding`, written when an edit falls back to a whole-project rebuild and carrying the reason it was declined, and `working`, written at most once a second between the files of each pass while a build runs. A client watching for a wedged analyser can then tell a slow rebuild from a stalled one. Neither frame is written until the client asks, because a client that does not know them would read them as a protocol error. Clients gate the request on the `progress-frames` capability in the `listen` frame.

**A compiler built for wasm serves analysis too, with one thread.** It reads the protocol through the same reflective `Json`, which on wasm needs the compiler built with `--rtti`. With no thread to read on, a frame is read only when the despatcher waits for one, so the three things that depend on reading while the analyser is busy are absent there: queries answered mid-compile, an edit cutting a compile short, and the idle timeout. `listen` leaves out `mid-compile-queries` and `compile-abort` accordingly, and `add-references` too, since that build reads no assemblies. The heap watchdog has no heap figure to read there and never recycles.

**A query that arrives while a compile is running is answered during it.** The despatcher pauses at each per-file boundary of the compile-expressions walk, answers whatever queries are already queued, and resumes. Previously such a query waited for the whole compile, which on a compiler-sized project is ~183 ms for the debounced one and seconds for a cold one.

The boundary is the one point during a compile at which the retained state is as consistent as it is between requests: every file's declarations, ancestries and types are resolved before the walk begins, and both the scope stack and the namespace stack are back at their base between files. Earlier passes of a from-scratch rebuild are repopulating the symbol table and answer nothing reliably, so nothing is served during those.

What gets served is a query that fails safe — one whose answer is either right or absent. A file the walk has not yet reached has no expression-level uses, so a hover or a definition over it answers emptily, exactly as it would have done a moment before the compile started. The whole-project queries — references, implementations, rename — are deliberately excluded: they answer with a *set*, and a set built from a use map still being rebuilt is incomplete rather than absent, which reads to a client as a complete one. Those keep waiting for the compile.

Recompiles are suspended while a mid-compile query is served, so a query miss answers from current state instead of starting a second compile inside the first.

Nothing on the wire changes. Responses are matched per kind — each `kind` has its own FIFO — never by global order, and the query-miss path already emitted an out-of-band `"query"`-phase diagnostics frame ahead of a query's own response, so a client that simply waits for its response is served exactly as before. The `mid-compile-queries` capability in the `listen` frame is there for a client that wants to pipeline queries against a compile and know it will get answers rather than a stall.

**An edit that arrives while a compile is running cuts that compile short.** The rest of the walk would compute diagnostics the edit has already made stale, so at each of the same per-file boundaries the analyser checks whether an `edit` or `edit_delta` is waiting and, if one is, stops. The compile is answered with its own `diagnostics` frame carrying `compile_needed: true` and no diagnostics or `checked_paths`, because the reliance judge that runs after the walk never ran and what the store holds for the files it did reach is therefore incomplete. The edit is handled next and answers as usual.

Each file's expression diagnostics are cleared as that file is walked rather than for every file before the walk starts, which is what makes abandoning it safe to do at any boundary. Clearing up front would leave every unreached file recorded as a path with nothing against it, and the next frame to report the store — the superseding edit's own — would tell the client those files had come back clean, dropping squiggles the user can still see a problem for. Cleared per file, an abandoned walk leaves the files it did not reach holding what the previous compile left, which is what an edit's own rebuild leaves them holding anyway.

Only the expressions-only walk is abandoned this way. Stopping part-way through it leaves the remaining files at up-to-expressions with no use-map entries, which is the state a single-file `edit`'s rebuild leaves anyway and which `is_full_compile_needed` already describes. The whole-project rebuild has no such halfway state and runs to completion, as does the recompile a query miss drives — that one is answering a question rather than refreshing diagnostics.

Clients must not write an edit during a compile without seeing the `compile-abort` capability in the `listen` frame. An analyser without it reads the edit only once the compile it should have interrupted has finished, so the client pays the wait it was trying to avoid *and* holds no edit back to shorten the next one.

The idle exit is advertised as the `idle-exit` capability in the `listen` frame. An analyser that cannot wait with a timeout waits for the next request however long it takes and does not advertise it, so a client must not expect an `exit` frame from one that lacks it. The paragraph below describes an analyser that has it.

The analyser also exits when it has been left alone. `--analysis-idle-timeout <seconds>` (default 1800, `0` to disable) bounds how long it will wait for a request before writing an `exit` frame and exiting **0**. A warm analyser retains the whole symbol table, so an editor window left open overnight holds hundreds of megabytes to answer nothing; the cold rebuild the next request pays is the cheaper side of that trade.

The timeout is armed only while waiting for a request — `read_request_or_timeout` in `protocol/` — so it can neither interrupt a response mid-frame nor be tripped by a slow compile, however long the compile takes. That leaves one race: a request that lands between the wait expiring and the process going is lost, which reaches the client as a request answered by the pipe closing. Clients handle that case already, for crashes and recycles.

**`exit` and `restart` mean opposite things to a client.** `restart` asks to be relaunched immediately (the process exits 1); `exit` says the analyser is going *because* nobody is asking anything, so a client should drop its handle and spawn a replacement only when it next has something to ask. A client that relaunches eagerly on `exit` converts an idle process into a periodic whole-project recompile. The exit status carries the same distinction for a client that was not reading at the time.

Wire field names are the ghūl property names verbatim (snake_case); no `JsonNamingPolicy` is applied. JSON escapes literal newlines inside strings, so a message never contains a raw newline — `read_line` on either end is a complete framing primitive. Multi-file EDIT requests fit on a single line, with each file's source text escaped inside its JSON string.

EDIT and COMPILE each produce a single `diagnostics` response carrying the diagnostics list plus a `phase` field (`"partial"` after EDIT, `"full"` after COMPILE), `elapsed_ms`, and `compile_needed` inline — replacing the previous two-frame answer. The set of files the analyser knows about and has just checked rides in `checked_paths`, so the client can clear stale squiggles for files whose entries don't appear in the diagnostics list.

`edit_delta` is EDIT with each file's text given as the one span that changed — `path`, a 1-based end-exclusive `start_line`/`start_column`/`end_line`/`end_column`, the replacement `new_text`, and `expected_length` — rather than in full. The analyser splices the span into its own retained copy of the file and then takes exactly the EDIT path with the reconstructed text, so the answer is the same `diagnostics` frame, and an interface-preserving delta reaches the incremental body re-walk like any other interface-preserving edit. What it saves is transport: a whole-file send costs the size of the file on every keystroke, almost all of it text the analyser already has.

**A delta is valid only for a file this client has already sent as full text in an `edit` request.** The analyser retains a file's text only when an `edit` carried it; the parse the analyser does of the project's own source files reads them straight into a tree and keeps no text, so having parsed a file — even having reported diagnostics for it — is *not* sufficient, and neither is the file existing on disk. A client that assumes any project file qualifies recycles the analyser on the first keystroke in each file the user opens.

What a client must do, then: send full text the first time it edits a given file, send full text for every open file again after an analyser restart, and send deltas only for files it has itself sent since. Keeping the two copies in step is the client's job throughout — send whole text whenever the analyser's text is not known.

`expected_length` is where that is checked rather than negotiated: a mismatch, or a delta for a file whose text the analyser does not hold, recycles the analyser, because a span spliced into text it wasn't computed against produces a plausible file rather than a failure and every later delta compounds it. The client re-primes the replacement process with full text as it does after any restart. Clients must not send the request without seeing the `edit-deltas` capability in the `listen` frame: unknown JSON members are ignored, so an older analyser reads a delta as an EDIT whose source is empty and blanks the file.

`hover_map` is a batch variant of `hover`: given a file path it returns every recorded hover for that file as a list of `entries`, each `{ start_line, start_column, end_line, end_column, description }` — so a tool can collect a whole file's hovers in one response instead of probing position by position. Each `description` is laid out against the same column budget `hover` uses, so a wide signature arrives as several newline-separated lines. `semantic_tokens` shares the same shape, returning `tokens` with `start_line`/`start_column`/`end_line`/`end_column`/`token_type`/`modifiers`, where `token_type` is one of VS Code's LSP semantic-token names (`class`, `interface`, `struct`, `enum`, `enumMember`, `typeParameter`, `namespace`, `method`, `function`, `property`, `variable`, `parameter`) and `modifiers` is a possibly-empty comma-separated list (currently `static` and `readonly`). Symbol uses whose kind has no LSP mapping contribute no token. `hover_map` itself never recompiles; the caller drives an `edit` (and/or `compile`) first. `semantic_tokens` adds a one-off `compile_all` fallback when the recorded-use map is empty, so a caller that hasn't yet sent `compile` still gets a populated response.

`add_references` adds assemblies, by path, to the reference set of a running analyser: the earlier cells of an interactive session, which exist only once the session has compiled them. It is answered by an `add_references` frame whose `message` says why an assembly could not be added, and is null otherwise. Naming an assembly already in the set is harmless; a different assembly under a name the set already holds is refused, as the compile server refuses it, since the two share the reference set's import. Any file can resolve differently against the larger set, so the next build is a whole-project rebuild rather than an incremental one. Clients must not send it without seeing the `add-references` capability in the `listen` frame: an older analyser fails the request as unknown.
